# Ship (MVP Phase D)

Status: design, 2026-10-07. Phase D of `docs/mvp-roadmap.md`: "Dockerfile and compose with Caddy, deploy runbook, the full Playwright scenario in CI, dependency bumps." The plan is `docs/superpowers/plans/2026-10-07-ship.md`.

## Why

After Phase C the app can run an HOA meeting end to end, but only on a developer's machine. Nothing builds an image, nothing has ever run `node dist/index.js` against a production install, and the web app has never been served by Express under its security headers: development uses Vite, and the Playwright harness uses `vite preview`. This phase puts Robbie on `https://robbie.scouch.dev` on one small VPS, with backups, a runbook a non-developer could follow on the night of a meeting, and CI that proves the image starts, serves the app and restores from a backup.

`spec.md` M12 already surveyed the target and decided several things (hosting, Resend, Caddy, the domain); this design follows it and says where it differs.

## Decisions

- **One VPS, Docker Compose, three long-running services plus a backup sidecar.** `app` (one image: shared, the backend and the built web app; Express serves the web build and its SPA fallback on the same origin as `/api` and `/socket.io`), `db` (`postgres:16-alpine`, a named volume), `caddy` (automatic HTTPS for `robbie.scouch.dev`, reverse proxy to `app`, WebSocket upgrades pass through), and `backup` (the same Postgres image running a nightly `pg_dump` and an uploads tarball). Out of scope: Kubernetes, more than one server, a CDN, the mobile store release.
- **The production files live in `deploy/`**: `deploy/compose.yaml`, `deploy/Caddyfile`, `deploy/.env.production.example`, `deploy/backup.sh`, `deploy/restore.sh`, `deploy/app-start.sh`, and the CI override `deploy/compose.ci.yaml`. The `Dockerfile` and `.dockerignore` are at the root (the build context is the monorepo). The development `docker-compose.yml` is untouched. Naming the production file `compose.yaml` inside `deploy/` means every command on the server is a plain `docker compose ...` run from that directory. (`spec.md` M12 named it `docker-compose.prod.yml`; the directory makes the suffix unnecessary.)
- **The image keeps the monorepo layout** (`/app/shared`, `/app/backend-node`, `/app/frontend-unified/dist`, hoisted `/app/node_modules`), because the backend finds the web build at `../../frontend-unified/dist` from its own `dist/` and the `file:../shared` workspace link resolves through it. No path changes in the code.
- **Migrations run when the container starts**, before the server listens: `deploy/app-start.sh` runs `prisma migrate deploy` and then `exec node dist/index.js`, so Node is PID 1's replacement and receives `docker stop`'s SIGTERM (the graceful shutdown in `index.ts` then runs). This needs the Prisma CLI in the runtime image: `prisma` and `dotenv` move from development to production dependencies of `backend-node` (see Findings).
- **Images are built by CI and pulled by the server.** `spec.md` M12 records that the VPS (1 vCPU, 1.9 GiB RAM) should not build images: the Vite and TypeScript builds can exhaust its memory. Every pull request builds and smoke-tests the image without pushing it; a push to `main` also publishes it to GitHub Container Registry as `ghcr.io/eudaimonstro/robbie:main` and `:sha-<7 hex>`. The server runs a tag named in its `.env` (`ROBBIE_IMAGE`), so an upgrade is pull and up, and a rollback is the previous tag. Building on the server (`docker compose build`) stays possible as a fallback, with the swap file the runbook adds. This differs from the decision as handed over ("pull, build, up"); the publishing is its own task so the owner can drop it.
- **Production refuses to start when misconfigured.** The existing start-up check (`signInStartupCheck`) becomes `startupCheck` and, in production, refuses: no `DATABASE_URL` (today the meetings silently fall back to memory), no email provider, no `EMAIL_FROM` (the fallback sender `noreply@robbie.app` is a domain nobody here owns; `spec.md` asked for this), neither `APP_URL` nor `CLIENT_ORIGIN`, and `ENABLE_TEST_AUTH=true` (today only a warning that it is ignored). It warns when `TRUST_PROXY` is unset in production, since behind Caddy every client would then share one rate-limit bucket. The image sets `NODE_ENV=production` and never runs in another mode (the logger loads `pino-pretty`, a development dependency, in any other mode).
- **The health check reaches the database.** `GET /api/health` answers 200 `{ status: 'healthy', mode }` only when `SELECT 1` succeeds within 2 seconds, else 503 `{ status: 'unhealthy', mode }`. The image's `HEALTHCHECK` and `docker compose up --wait` rely on it. (In-memory mode, development only, has no database to ping.)
- **Email is Resend over HTTPS**, as `spec.md` decided on 2026-10-05: DigitalOcean blocks outbound SMTP ports 465 and 587 on this droplet. `RESEND_API_KEY` (a sending-only key for the verified domain `robbie.scouch.dev`) and `EMAIL_FROM="Robbie <noreply@robbie.scouch.dev>"`. The SMTP and SendGrid providers stay in the code and in the example file, documented as alternatives for another host.
- **Backups are a compose sidecar, not host cron.** It ships with the stack, is versioned in the repo, starts with `docker compose up -d`, and the same script is the manual backup (`docker compose run --rm backup once`) and what CI exercises. Each night after `BACKUP_HOUR_UTC` (default 9, which is 3 or 4 a.m. in Chicago) it writes `robbie-<stamp>.dump` (`pg_dump --format=custom`) and `uploads-<stamp>.tar.gz` to `deploy/backups/` on the host, keeps `BACKUP_KEEP_DAYS` (default 14) days, and makes the files the deploy user's. Copying them off the server is a documented step (the VPS failing would take both copies). A backup is kept only once `pg_restore --list` and `tar -tzf` read it back, and old ones are deleted only after a good one. Restore is `deploy/restore.sh`, tested in CI on every pull request: it restores into a scratch database and unpacks into a scratch folder, and swaps them in (the databases by renaming, in one transaction) only when both succeeded, so a damaged backup changes nothing.
- **The web app is served with long-lived caching for hashed bundles and none for `index.html`**, so a deploy reaches the next page load, and a missing bundle is a 404 rather than `index.html` (a browser holding an old page gets a clear failure, not a JavaScript MIME error).
- **The Content Security Policy is Helmet's default without `upgrade-insecure-requests`.** Caddy redirects HTTP to HTTPS and Helmet already sends HSTS, so the directive adds nothing in production, and without it the same image works over plain `http://localhost` in CI and on a developer's machine.
- **The per-IP sign-in limits go up**: 100 code requests and 200 verifications per address per 15 minutes (from 10 and 20). On the night of a meeting, every homeowner on the clubhouse Wi-Fi shares one public address; at 10 per 15 minutes the eleventh homeowner can't get a code. The per-email limits (5 codes an hour, 5 attempts per code) remain the guard against guessing.
- **The Playwright harness runs on the production path.** The existing `e2e` job already runs every spec (smoke, header, visual, import, the meeting scenarios) on each pull request. The harness switches from `vite preview` to the API serving the built web app itself, so every e2e test exercises Express's static serving, the SPA fallback and the CSP in a real browser, and a smoke test fails on any CSP violation.
- **The full acceptance scenario becomes a test**: `e2e/tests/annual-meeting.spec.ts` runs the seeded 2026 Annual Meeting (`MAPLE1`) as roadmap steps 5 to 14 describe it, within what the app offers (see "The annual meeting test").
- **CI audits production dependencies** (`npm audit --omit=dev` on the three shipped workspaces), failing on critical findings; the high findings it will report are listed and accepted below.
- **The mobile app points at the new server.** `mobile/app.config.js` and `mobile/app.json` still name a Railway URL; the production URL becomes `https://robbie.scouch.dev`. No other mobile change.

## The image

A multi-stage `Dockerfile` on `node:24-slim`:

- **build**: installs OpenSSL (Prisma's schema engine reads its version), `npm ci -w shared -w backend-node -w frontend-unified --include-workspace-root` (Expo's tree never enters), then builds shared, the backend (`prisma generate && tsc`) and the web app.
- **runtime**: OpenSSL, `NODE_ENV=production`, the four workspace `package.json` files and the lockfile, `npm ci --omit=dev -w shared -w backend-node --include-workspace-root=false` (about 180 packages before `prisma` joins), the three `dist` folders, `backend-node/prisma` and `prisma.config.ts`, `/data/uploads` owned by `node`, `USER node`, `EXPOSE 3001`, `HEALTHCHECK` with Node's `fetch` (the slim image has no curl) and `CMD ["app-start"]`. `CHECKPOINT_DISABLE=1` stops the Prisma CLI's update check.

`.dockerignore` keeps out `node_modules`, every `dist`, `.env` files, the generated client, uploads, `e2e`, docs and all of `mobile` but its `package.json` (the lockfile check needs every workspace's manifest).

## Compose and Caddy

`deploy/compose.yaml`: `app` (image `${ROBBIE_IMAGE:-ghcr.io/eudaimonstro/robbie:main}`, with a `build` section for the fallback; `env_file: .env`; `NODE_ENV`, `PORT`, `TRUST_PROXY=1`, `UPLOAD_DIR` and `DATABASE_URL=postgresql://robbie:${POSTGRES_PASSWORD}@db:5432/robbie` set by compose; the `uploads` volume; waits for a healthy `db`; `stop_grace_period: 15s`), `db` (user and database `robbie`, `pg_isready` health check, `pgdata` volume, no ports), `backup` (above), `caddy` (`caddy:2.11-alpine`, ports 80, 443 and 443/udp, `caddy_data` and `caddy_config` volumes). Every service logs through `json-file` with rotation. Only Caddy publishes ports.

`deploy/Caddyfile`: the site `{$ROBBIE_DOMAIN}` with `encode zstd gzip` and `reverse_proxy app:3001`, and the ACME account email from `{$ACME_EMAIL}`. Caddy proxies WebSocket upgrades and sets `X-Forwarded-For` without extra configuration. The DNS record stays DNS-only (gray cloud) so Let's Encrypt's HTTP-01 challenge reaches Caddy (`spec.md` M12).

`deploy/.env.production.example` documents every variable the backend reads (`DATABASE_URL`, `DIRECT_URL`, `DATABASE_SSL`, `NODE_ENV`, `PORT`, `TRUST_PROXY`, `UPLOAD_DIR`, `APP_URL`, `CLIENT_ORIGIN`, `EMAIL_FROM`, `RESEND_API_KEY`, `SENDGRID_API_KEY`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_SECURE`, `LOG_LEVEL`, `ENABLE_TEST_AUTH`, `TEST_VERIFICATION_CODE`), plus compose's own (`ROBBIE_DOMAIN`, `ACME_EMAIL`, `ROBBIE_IMAGE`, `POSTGRES_PASSWORD`, `BACKUP_HOUR_UTC`, `BACKUP_KEEP_DAYS`, `BACKUP_OWNER`), saying for each whether to set it, leave it, or never set it. The server's copy is `deploy/.env` (gitignored by `**/.env`).

## CI

- **`ci` job**: gains `npm audit --omit=dev -w backend-node -w shared -w frontend-unified --audit-level=critical`.
- **`e2e` job**: unchanged in shape; the harness it runs now serves the web app from the API, and the new annual meeting spec runs with the rest.
- **`image` job (new)**: builds the image with Buildx and the GitHub Actions cache, loads it as `robbie:ci`, checks that the image refuses to start with `ENABLE_TEST_AUTH=true` and with no email provider, starts `app` and `db` from `deploy/compose.yaml` plus `deploy/compose.ci.yaml` (which publishes the app on `127.0.0.1:3001`) with dummy secrets, waits for health, then checks: `/api/health` is healthy, `/` and a deep link `/meetings/ABC123` are the web app with `Cache-Control: no-cache` and a CSP, a bundle under `/assets/` has an immutable cache header, a missing bundle is a 404, and an API path signed out is a JSON 401, never the web app. It then makes a backup, changes the database and the uploads, restores, and checks both are back. Compose logs are printed on failure; everything is torn down at the end. On a push to `main`, it logs in to GHCR with `GITHUB_TOKEN` and pushes the two tags.

## The annual meeting test

A code read (not a run) of the meeting screens shaped how the roadmap's scenario becomes a test, since a few steps work differently from the roadmap's words:

- **The test owns its data.** It reseeds the demo before it starts and after it ends (the global setup's reset, moved into `e2e/demo.ts`), so a retry starts from a fresh `MAPLE1` and the other specs see the demo as the global setup left it.
- **The 2025 minutes** are approved with the console's "Approve as read" once their agenda item is called; the app has a dedicated approval rather than unanimous consent, and nothing shows before the call to order.
- **The treasurer's attachment**: the demo has none, and the app offers no way to add one to an already scheduled meeting (the uploader exists only while scheduling). The test links a document to the treasurer's item through the API (`POST /api/attachments/link-document`) as Pat before the meeting, then opens it from the console. The missing UI is a product gap, recorded below.
- **The bylaw amendment** is moved from a phone (the console's floor motion leaves out bylaw amendments), seconded, debated with the queue on the display, and carried by two thirds with phones plus the room; the bylaws then read version 2 with the 15% text. The seeded draft amendment "Lower the quorum to 15%" is not what the meeting uses; the sync creates its own amendment.
- **Two directors are two elections** ("Director, seat 1" and "Director, seat 2"): an election elects one person, and a person can't be nominated twice for one position.
- **After**: Pat publishes the generated minutes, enables the bylaws' share link, and a signed-out browser reads version 2 there; the 2025 minutes show as approved.

## The runbook

`docs/deploy.md`, written for the owner and anyone helping on a meeting night: what runs where; host preparation (the Compose plugin, a `deploy` user instead of the `docker` group for `steve`, a 2 GB swap file, `ufw` for 80 and 443, SSH only over Tailscale, all from `spec.md` M12); DNS (the existing DNS-only A record, and Resend's DKIM, SPF, bounce MX and a DMARC record); the first deploy; the first owner (sign in, accept the terms, create the organization, which makes its creator the owner; never the demo seed); a test email; upgrades (a backup first, pull, up; migrations run on start; never within a day of a meeting); rollback (the previous image tag, and the pre-upgrade dump when a migration must be undone); backups (where, when, how long, copying them off the server) and the restore procedure, including onto a fresh server; logs; and a checklist for the night of an HOA meeting (the display on the TV, Wi-Fi and a cellular fallback, the QR code scanned on both, one real sign-in on the venue Wi-Fi, the meeting's chair, agenda, quorum settings and last year's minutes, and the paper fallback the floor counts give).

## Known gaps accepted for the MVP

- No UI to add an attachment to a scheduled meeting after scheduling (the test uses the API).
- Anyone who can receive email can sign in and create organizations on the server (each user's organizations are limited in number). Fine for one HOA; an allowlist is a later decision.
- `/api/health` doesn't check the email provider; a test email is a runbook step.
- One server: a restart mid-meeting reconnects phones (presence survives 90 seconds), but there is no failover.
